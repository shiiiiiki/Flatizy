Коротко и без воды — что нужно реализовать на фронте / в сторонних сервисах для Webhook + TLS

1) Публичный HTTPS (TLS 1.3)
   - Обеспечить публичный HTTPS URL для webhook (например https://yourdomain.com/telegram/webhook) — можно использовать ngrok/Cloud Run/VM с проброшенным 443.
   - Сертификат: предпочесть валидный CA; для локального теста сгенерировать keystore (см. файл SUMMARY).
   - Убедиться, что endpoint доступен по HTTPS и поддерживает TLS 1.3.

2) Конфигурация в приложении (backend)
   - В `application.properties` установить `telegram.webhook.url` = публичный URL.
   - Сгенерировать и задать `telegram.webhook.secret-token` (hex32).
   - Если backend сам регистрирует webhook — он отправит secret token при регистрации (реализовано).

3) Безопасность / сетевые требования
   - Открыть/пробросить порт 443 или использовать туннель (ngrok) с HTTPS.
   - Если есть reverse-proxy (nginx) — пробрасывать X-Telegram-Bot-Api-Secret-Token и HTTPS на приложение.

4) Тестирование webhook (фронт не обязателен — но удобно для CI)
   - Для ручной проверки: отправить POST на `https://.../telegram/webhook` с заголовком `X-Telegram-Bot-Api-Secret-Token: <value>` и JSON-полем `updateId`.
   - Примеры команд в SUMMARY.

5) Логи и хранение
   - Логи webhook: только мета (updateId, type, userId). Не хранить тексты сообщений/пользовательские данные в БД.
   - Для аудита можно включить централизованный лог (ELK/Graylog), но не хранить пользовательские payloads.

6) Реакция Telegram/Биллинг/Другое
   - Если требуется, чтобы сторонний сервис (биллинг) отправлял уведомления в Telegram через наш webhook — он должен вызывать публичный HTTP(S) endpoint нашего приложения (не напрямую в Telegram).

7) Документация для фронтенда / devops (что им нужно сделать)
   - Указать публичный webhook URL в приложении (`telegram.webhook.url`).
   - Передать secret-token команде, которая будет настраивать Telegram webhook (если ручная регистрация).
   - Обеспечить доступность 443/TLS 1.3.

Secrets management — хранение BOT_TOKEN и ключей (уровень 2)

- Что закрывает: предотвращает компрометацию токена доступа (BOT_TOKEN) в репозитории или в коде.

- Что реализовать (коротко):
  1) Хранить `TELEGRAM_BOT_TOKEN` вне кода — в переменных окружения, Docker secrets или в секретном хранилище (HashiCorp Vault, AWS Secrets Manager, Azure Key Vault).
  2) Удалить жестко прописанный токен из `src/main/resources/application.properties` и в качестве значения использовать ссылку на env var или секрет (например `telegram.bot.token=${TELEGRAM_BOT_TOKEN}` — Spring умеет читать ENV переменные `TELEGRAM_BOT_TOKEN`).
  3) Автоматизировать ротацию ключей: сгенерировать новый токен в BotFather, обновить секрет в хранилище, применить конфиг (rolling deploy), проверить работоспособность, затем отозвать старый токен.

- Примеры (минимум слов):
  - Локально (Windows PowerShell):
    $env:TELEGRAM_BOT_TOKEN = "<new-token>" ; Start-Application
  - Docker compose: использовать `environment:` или `secrets:` и не сохранять токен в репозитории.
  - Vault: поместить секрет под путь `secret/flatizy/telegram` и читать через Spring Cloud Vault.

- Проверка после ротации:
  1) Обновить секрет в хранилище.
  2) Перезапустить приложение/выполнить rolling deploy.
  3) Отправить тестовый update на `/telegram/webhook` (curl с заголовком `X-Telegram-Bot-Api-Secret-Token`) или проверить логи на успешную регистрацию webhook.

- Рекомендации:
  - Не хранить значение токена в VCS.
  - Привязывать действия ротации к процедурам CI/CD (скрипт: обновить секрет -> развернуть -> smoke-test).
  - Период ротации: завести политику (например, каждые 90 дней) или при подозрении на компрометацию.
